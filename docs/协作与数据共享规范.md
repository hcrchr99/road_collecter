# RoadCheck 团队协作与数据共享规范

> 适用：本项目所有成员与其 AI Agent
> 版本：v1.0（2026-09-18）
> 配套仓库：https://github.com/hcrchr99/road_collecter

---

## 0. 为什么需要这份文档

项目推进到现在，代码已经在 GitHub 上共享了，但**数据完全没有共享途径**：

- 采集包 `*.zip` 被 `.gitignore` 排除（这是对的，含 GPS 轨迹）
- 但排除之后，没有建立任何替代通道
- 结果：每个人只能用自己的数据，别人采的坑洼、别人标的事件，你用不到

更麻烦的是**多 agent 并发的场景**：如果两个 agent 同时写同一份标注表，后写的会静默覆盖先写的，而且没有任何提示。这类损失是不可逆的。

这份文档要解决的就是：**哪些数据该共享、走哪条通道、怎么避免互相踩踏。**

---

## 1. 核心原则

### 1.1 按「敏感度」分层，不按「文件类型」分层

一个常见的错误分类方式是「代码放 Git，数据放网盘」。这在本项目上是错的，因为我们有**四种敏感度完全不同**的数据：

| 层 | 内容 | 敏感度 | 通道 |
|---|---|---|---|
| **L1** | 代码、自检报告、文档 | 无。合成数据产出，可复现 | GitHub 公开 |
| **L2** | 合成演示数据（`examples/`、`demo_pack.zip`） | 无。虚构坐标 | GitHub 公开 |
| **L3** | **真实采集包**（samples / frames / GPS） | **高**。可反推居住地与出行规律 | 私有通道，仅在团队内 |
| **L4** | 标注集、黄金集 | 中。人力的产出，怕覆盖 | 私有 + 版本化 |

**关键区分：L3/L4 的约束是「不对外发布」，不是「不共享」。** 团队内部必须共享，否则项目做不下去。README 里写的「不发布原始轨迹」指的是**对外发布**（提交材料、公开链接、演示视频），跟内部协作不冲突。

### 1.2 共享「输入 + 脚本」，不共享中间产物

`out/`、`vis/`、`fused/` 这些目录**不应该被共享**。它们是 `analyze.py` 的确定性输出，别人拿到输入和脚本，跑一遍就有。共享它们只会带来：

- 版本漂移（你的 out/ 是旧代码跑的，我的不是）
- 体积膨胀（每份几百 KB 到几 MB，还有帧图）
- 溯源困难（看到一份 out/events.csv，不知道是哪版代码产的）

**唯一例外**：要拿去给评委看的最终产物（如 `examples/demo_output/`），这类要有明确的「这是交付快照」标注。

### 1.3 源数据只读

`data/raw/` 一旦落盘，**永不复写、永不重命名、永不在原地编辑**。

如果发现某份采集包有问题（比如上一轮那个速度门控全 0 的包），**不要修它**，而是：

1. 原包保持不动
2. 把诊断结论写进 `data/raw/<pack_id>.notes.md`
3. 需要修正数据时，产出新文件 `<pack_id>.fixed.zip`

这样才能保证「任何一个结论都能回溯到当时用的那份原始数据」。如果你覆盖了原包，那 `replay_report.txt` 里的数字就永远对不上了。

## 3. 采集包登记表（MANIFEST.csv）

这份表是整个共享机制的枢纽。它回答了「团队现在有哪些数据、谁采的、标到哪一步」。

### 3.1 字段定义

| 字段 | 含义 | 示例 |
|---|---|---|
| `pack_id` | 全局唯一 ID，= 文件名去扩展名 | `roadcheck_20260918_2127` |
| `collected_by` | 采集人 | `alice` |
| `collected_at` | 采集时间（本地时区） | `2026-09-18T21:27:33+08:00` |
| `mode` | 采集模式 | `bike` / `vehicle` / `handheld` |
| `duration_s` | 时长（秒） | `19.6` |
| `samples` | 样本数 | `1175` |
| `fs_hz` | 实测采样率 | `58.8` |
| `distance_m` | 里程（米，聚合值） | `0` |
| `event_count` | 检出事件数 | `8` |
| `sweep_count` | 扫描帧数 | `10` |
| `sha256` | 文件校验和（前 16 位） | `a3f9c21e8b7d4056` |
| `storage` | 存储位置 | `tdrive` / `nas` / `local:alice` |
| `label_status` | 标注状态 | `todo` / `wip` / `done` |
| `labeled_by` | 标注人 | `bob` |
| `notes` | 备注 | `速度门控全 0，见 notes` |

### 3.2 为什么不能只靠文件名

文件名只有时间戳，无法回答「这个包有没有人标过」。而且多人的时间戳可能撞车（不同时区、不同设备时钟）。`sha256` 能检测出「同名的两份文件内容其实不一样」这种隐蔽问题。

### 3.3 登记表怎么用

```bash
# 采集完一份新数据，自动登记
python tools/register_pack.py <采集包.zip> --collected-by alice --mode bike

# 看谁还没标
python tools/pack_status.py --status todo

# 标完了更新状态
python tools/register_pack.py --update roadcheck_20260918_2127 --label-status done --labeled-by bob
```

## 4. 多 Agent 并发的三条铁律

这是本规范里最重要的一节。多 agent 同时工作，最容易出的不是「写错」，而是「静默覆盖」。

### 铁律 ① 一人一档 —— 每个 agent 只写自己的文件

**绝对不要**让两个 agent 往同一个 `labels.csv` 里追加行。

正确做法：**按 `pack_id` 切分文件**。

```
data/labels/roadcheck_20260918_2127.labels.csv   ← 只有 alice 的 agent 能写
data/labels/roadcheck_20260919_0900.labels.csv   ← 只有 bob 的 agent 能写
```

需要汇总时，用一个**只读的合并脚本**产出 `labels.all.csv`（这个文件本身也不该被手写）。

**如果必须多人标同一份包**，则按帧号区间分工：

```
data/labels/roadcheck_20260918_2127.part-alice.csv   帧 0-499
data/labels/roadcheck_20260918_2127.part-bob.csv     帧 500-999
```

合并 = 两边拼起来，无冲突。

### 铁律 ② 源数据只读 —— 见 1.3

一个具体建议：把 `data/raw/` 在共享盘上设为**只读权限**，从物理上杜绝误改。新文件由采集者写入，之后谁都不能改。

### 铁律 ③ 写文件用「原子写」—— 避免读到半截文件

多 agent 场景下，一个 agent 正在写 `labels.csv`，另一个 agent 去读它，可能读到写了一半的内容。这是最隐蔽的 bug。

正确做法：

```python
import os, tempfile

def atomic_write_csv(df, path):
    """先写临时文件，再原子替换。读方永远看不到半截文件。"""
    d = os.path.dirname(os.path.abspath(path))
    fd, tmp = tempfile.mkstemp(dir=d, suffix=".tmp")
    os.close(fd)
    try:
        df.to_csv(tmp, index=False, encoding="utf-8-sig")
        os.replace(tmp, path)      # 原子操作
    except Exception:
        if os.path.exists(tmp):
            os.remove(tmp)
        raise
```

`os.replace()` 在 Windows 和 POSIX 上都是原子的。这个习惯能省掉大量「明明写了却读出来是空的」的调试时间。

## 5. 三条通道的具体选择

### 5.1 通道一：GitHub（L1 + L2）

已经跑通了。你现在的用法就是对的：

- 代码、报告、文档、schema → 提交
- 采集包、中间产物 → `.gitignore` 排除

**要注意的一件事**：`reports/*.txt` 是**脚本产出的**，所以改代码后必须重跑，否则会出现「报告写着 ±200ms，代码其实是 ±1200ms」这种脱节（这次就发生了）。建议在 `README` 里加一句工作流约定：

> 任何会改变输出数字的代码改动，提交前必须重跑 `reports/` 下对应报告。

### 5.2 通道二：对象存储 / 网盘（L3 + L4）

你们已经有**项目 Drive（tdrive）**可用了，这是现成的选择。放置结构就是 2.2 节那样。

**如果数据量大（GB 级）**，tdrive 可能不够，可以选：

| 方案 | 适合场景 | 注意 |
|---|---|---|
| 项目 Drive / 腾讯文档 | 几百 MB 内，团队都用腾讯系 | 最省事，权限跟项目走 |
| 私有 GitHub 仓库 | 只放标注文本（小文件） | 免费，但**别放采集包**（LFS 有配额） |
| 阿里云 OSS / 腾讯云 COS | 大文件、需程序化访问 | 要配密钥，记得别提交到仓库 |
| 学院 NAS / 内网共享盘 | 校内团队 | 最稳，但校外访问需 VPN |

**无论选哪个，都必须加两个约束：**

1. `raw/` 目录设只读，只有采集者本人首次写入
2. 上传时同步更新 `MANIFEST.csv`（可以配一个脚本自动算 sha256）

### 5.3 通道三：本地工作区（无状态）

每个 agent 的本地工作区**不应该保存任何别人需要的东西**。规则很简单：

- 从 GitHub 拉代码
- 从共享盘拉自己需要的采集包到 `data/raw/`
- 跑脚本
- 产出留在本地，不共享

## 6. 标注流程中的并发约定

结合之前定的流程（先采数据 → 手工标注 → 跑识别），标注环节最容易出并发问题。约定如下：

### 6.1 分工优先按「包」分，其次按「帧区间」分

```
# 优先：整包分配，零冲突
alice → roadcheck_20260918_2127, roadcheck_20260919_0900
bob   → roadcheck_20260919_1430, roadcheck_20260919_1730
```

### 6.2 黄金集必须锁定

`data/golden/` 下的 100 帧纯人工标注是**评估基准**，一旦开始用来评估模型，就**不能再改**。

建议做法：标完后计算一次哈希，写进 `data/golden/<pack_id>/README.md`：

```markdown
标注人：alice
标注日期：2026-09-20
依据：labels/schema.md v1.0
内容哈希：sha256=8f3a2b1c...
状态：FROZEN —— 已用于评估，不得修改
```

**要改就得新建一份 `golden.v2/`**，并在 README 里说明改了什么、为什么。这样任何一次评估结果都能对应到确切的黄金集版本。

### 6.3 标注冲突的处理

如果两个人都标了同一份包（比如为了算标注一致性），**不要合并成一份**，而是：

- 各自保留
- 跑一个比对脚本输出分歧清单
- 双方对分歧逐条讨论，结论写进第三份 `adjudicated.labels.csv`，并注明依据

**这个「双人标注 → 分歧 → 仲裁」的过程本身就是有价值的产物** —— 它能算标注者一致性（Cohen's Kappa），写进方案文档是加分项，说明你们的真值可靠。

## 9. 两个容易忽略的点

### 9.1 提交前必须验证忽略规则真的生效

`.gitignore` 写错是很常见的，尤其是有例外规则（`!`）的时候。你们的 `.gitignore` 里就有：

```
_*.txt
!reports/*.txt
```

建议每次改完 `.gitignore` 都跑一次：

```bash
git check-ignore -v data/raw/test.zip          # 应输出匹配的规则
git status --porcelain | grep -i zip           # 应无输出
```

**更稳妥的做法**：在提交前加一道自检，防止误提交采集包：

```bash
git ls-files | grep -iE '\.(zip|csv)$' | grep -v '^examples/' | grep -v '^labels/'
# 应无输出。有输出说明有不该入库的文件
```

### 9.2 别把密钥放进任何共享通道

地图服务的 key 是硬约束（README 已写）。补充一点：**共享盘上的脚本配置也可能泄密**。如果 `config.py` 里有 key，它就不该被上传到共享盘 —— 用 `config.example.py` + 本地 `config.py`（加进 `.gitignore`）的方式。
