二、问题二：为什么一直显示"定位不可用"

这是 v0.1 的真实 bug，不是你的操作问题 原代码在授权函数里先 await DeviceMotionEvent.requestPermission()，然后才调用 navigator.geolocation.watchPosition()。浏览器要求权限弹窗必须在用户手势的**同一次任务**里发起，await 之后手势已失效，定位弹窗被静默抑制——于是只有一个语焉不详的"定位不可用"。

三个真实原因（按可能性排序）

  1. 非安全上下文。直接用 file:// 双击打开 HTML 时，Chrome 会拒绝定位；http:// 的非 localhost 地址同样被拒。这是最常见的。
  2. 授权顺序错误。上面说的 await 消耗手势问题。
  3. 权限已被拒绝过。浏览器对你点过的"拒绝"有记忆，不会再次弹窗，只能手动到站点设置里改回允许。

v0.2 的修复内容

  • 三步式流程：环境自检 → 授权并试采 → 正式采集。未通过试采前，"开始采集"按钮保持禁用，不会让你白跑一趟。
  • 环境自检面板：逐项显示安全上下文（含当前协议）、运动传感器 API、授权方式（iOS 需主动请求 / Android 由浏览器设置控制）、定位与摄像头 API 可用性、以及能查到的权限状态（Safari 不支持查询时会如实标注）。
  • 授权顺序修正：在点击的同一任务里先同步发起 getCurrentPosition（触发定位弹窗），再 await 传感器授权。两者共用同一个用户手势。
  • 错误码翻译成可操作指引：PERMISSION_DENIED → 告诉你去哪改回允许；POSITION_UNAVAILABLE → 系统定位服务未开或室内无信号；TIMEOUT → 到室外、关省电模式。
  • 4 秒试采：真的采一段数据并报出实测采样率。低于 25 Hz 会提示可能是省电模式。
  • 8 秒看门狗：Android 上传感器被拒时不会报错，只是没有数据。看门狗负责把这种静默失败变成明确提示。
  • 可重复授权：授权按钮变为"重新授权 / 重新试采"，试采失败可随时重来。
你需要做的唯一一件事 把 collector.html 部署到 HTTPS 地址（Vercel 或 Cloudflare Pages，免费且几分钟完成），再从手机浏览器打开。本地双击文件打开是无法拿到权限的。

三、问题三：标定问题，以及为什么"换思路"比"标得更准"更对

你指出的问题很实在：井盖经过只有一瞬间，屏幕上还要看着路，盲点按钮大概率点不到、点错。任何试图提高"实时点击精度"的方案都有天花板。所以 v0.2 把标定从实时改成了确认式。

1自动抓帧（骑行中零操作）摄像头以 10 fps 存入一个 2.4 秒的环形缓冲。IMU 检出事件时，立刻从缓冲里取出该事件前后共约 1.6 秒的画面存下来——事件发生前的画面也留住了，因为检测本身有几十毫秒延迟。
2结束后的回看标定每条事件带 6 帧缩略图，看着图点标签。井盖、坑洼、减速带在图上清晰可辨，准确率与"骑行中盲点"完全不是一个量级。
3「误报」也是宝贵标签专设一个「误报」按钮。人体晃动、车辆振动造成的假事件被显式标出来后，就是降低误报的负样本——这比多标 10 个正样本更有价值。
4最终由视觉自动标注这才是根本解法：视觉模型逐帧判定路面状态，自动给每个事件贴上类型标签。人工只需要抽检少量结果做质量把关，不再需要逐条标定。

为什么人工标注仍然要保留：它有两个不可替代的作用——① 提供真实数据上的标定基准（视觉基线的阈值必须在真数据上重标）；② 产出「误报」负样本。但从工作量上说，它已经从"每骑行 1 分钟就要操作 1 次"降到"每趟骑行后花几分钟复核"。

四、问题一：视觉融合方案

4.1 为什么两个模态不是重复的

这是整个方案最需要讲清楚的一点，也是方案文档里的核心技术叙事：

模态它感知的物理量能识别的病害原理上的盲区
IMU 垂直方向的颠簸幅度与波形形态，本质上是深度与结构 坑洼、减速带、井盖、粗糙路面 抓不到不引起颠簸的病害：纵向裂缝、横向裂缝、龟裂、浅层修补。而这些在真实路面上占比极高——RDD2022 里裂缝类标注数量远超坑洼
视觉 路面的表面纹理与明暗结构，本质上是类型与形态 坑洼、裂缝（可细分为纵向/横向/龟裂）、粗糙路面、井盖 单目图像无法可靠估计深度——看不出坑有多深；且受夜间、逆光、积水反光影响
融合 深度 + 类型两个正交维度 病害类型覆盖 7/7；坑洼的置信度从单模态 0.70 提升到 0.95（双模态互证）

反过来也一样：井盖和减速带在图像上就是一块区域，靠纹理很难与坑洼区分，但它们的颠簸特征是结构性凸起——IMU 恰好能判断"这是凸起而不是凹陷"。这就是融合决策表里 R5 规则的价值。

一个必须做对的架构决定：周期扫描帧 如果只在 IMU 检出事件时才抓帧，那么裂缝永远不会被拍到——因为它不引起颠簸，压根不会触发抓帧。这样视觉就永远只能给 IMU 已发现的事件贴标签，贡献不了任何新的病害。所以 v0.2 增加了每 2 秒一次的独立扫描抓帧，与事件无关。扫描帧里发现的病害会成为"视觉独有"记录，这才是视觉真正的增量价值。

4.2 两个视觉后端

默认可用

经典 CV 基线

只需要 OpenCV，零模型依赖，装上就能跑。特征全部有明确物理含义：

五、本轮修掉的实现缺陷

这些都是实际跑出来的问题，记录在此以免重犯；其中前两个是关于"用什么特征"的方法论问题，值得写进方案的技术章：

问题现象与根因修法
绝对阈值在纯噪声上恒定误报 用"低于均值 0.9 倍标准差"判暗斑，在纯高斯噪声图像上恒有 18% 像素满足（因为这就是正态分布的固定尾概率），结果平滑路面全被当成坑洼 改为光照归一化后做相对亮度比较，再配合连通域面积过滤。暗斑占比从"平路 0.19 / 坑洼 0.06"变成"平路 0.0000 / 坑洼 0.0561"
Otsu 在近均匀图像上失效 裂缝掩码用 Otsu 自动阈值，但近均匀图像的直方图是单峰的，Otsu 会把噪声随意切开——实测把平滑路面的 60% 像素判成裂缝 改用固定绝对阈值（黑帽响应 > 28 灰度单位）。裂缝检出率 3/3，平滑路面误检率降为 0
合成图用逐像素噪声 拉普拉斯方差被独立噪声主导，结果"平滑路面"成了高频最高的一类，特征完全反了 改用空间相关噪声（模糊后的噪声）模拟沥青骨料纹理
井盖被裁掉一半 合成坑洼时未考虑 ROI 裁剪，部分样本被裁去大半，暗斑面积不足以触发阈值，导致坑洼召回只有 2/40 把病害限制在 ROI 可见区域内；坑洼召回恢复到 40/40
扫描帧节拍与用例时间不匹配 扫描帧只在偶数秒产生，而演示脚本把裂缝用例放在了 9、21、45 秒等奇数秒，条件永远不触发，4 处裂缝全部漏掉 用例时间对齐到扫描节拍，并加断言防止回归
两侧 id 体系不可比 IMU 侧用 analyze.py 重新检测事件（id 是自己的行号），视觉侧用采集端的事件 id。这次恰好都是 0–8 所以没暴露，但检测结果一旦多一个或少一个事件，全部 id 就会整体错位 不再依赖 id 相同，统一按时间戳对齐（±1200 ms），并在日志里明确打印"id 相同的个数不作为依据"

六、完整流水线

# 0) 部署采集端（必须 HTTPS），骑行采集，导出 roadcheck_xxx.zip

# 1) IMU 侧：事件检测 + 健康度指数
python analyze.py --input samples.csv --outdir out
#   -> out/events.csv  out/events.geojson  out/summary.json

# 2) 视觉侧：事件帧判定 + 扫描帧自动发现病害
python vision.py --zip roadcheck_xxx.zip --outdir vis
#   -> vis/vision_events.json  vis/vision_events.csv
#   装了 ultralytics 并训练好权重后加：--weights rdd2022_yolov8n.pt

# 3) 融合决策：双模态互证 + 视觉独有 + 空间去重
python fusion.py --imu out/events.csv --vision vis/vision_events.json --outdir fused
#   -> fused/fused_events.geojson（合规的聚合病害点，可直接叠地图）
#   -> fused/fused_summary.json（含覆盖度、互证数、去重数）

# 自检（都不需要任何外部数据）
python analyze.py --selftest
python vision.py  --selftest
python fusion.py  --selftest
python make_demo_zip.py        # 生成演示包后可跑通 1-3 全链路

八、下一步建议

按优先级：① 先把采集端部署到 HTTPS 并去采一趟真实数据——这是唯一能产出"别人替代不了"的资产，也是验证权限修复是否真的生效的唯一方式；② 采回来之后跑完整流水线，看真实帧上经典 CV 基线到底退化多少，这个数字决定你要不要在视觉模型上投入；③ 再决定是补 YOLO 还是先做展示端地图。
